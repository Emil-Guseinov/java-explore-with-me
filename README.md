# ExploreWithMe

Приложение для публикации событий и поиска компании для участия в них.

## Запуск

Нужны JDK 21, Maven 3.9 и Docker с Compose. В Windows перед запуском контейнеров
нужно открыть Docker Desktop. Команды выполняются из каталога с корневым `pom.xml`.

```shell
mvn clean install -P check
docker compose up --build -d
```

Адреса:

| Сервис | Адрес |
| --- | --- |
| Основной API | http://localhost:8080 |
| Статистика | http://localhost:9090 |
| Проверка основного сервиса | http://localhost:8080/actuator/health |
| Проверка статистики | http://localhost:9090/actuator/health |

Проверка контейнеров и остановка:

```shell
docker compose ps
docker compose logs ewm-service stats-server
docker compose down
```

Данные сохраняются в Docker volumes между перезапусками. Порты 8080, 9090, 5432
и 5433 должны быть свободны.

Для запуска приложений из IDE сначала поднимите только базы:

```shell
docker compose up -d ewm-db stats-db
```

Затем запустите `StatsApplication`, после него `EwmApplication`.
По умолчанию используются базы `ewm` на порту 5432 и `stats` на порту 5433.
Пары логин/пароль для локальной разработки: `ewm/ewm` и `stats/stats`.
URL и учётные данные меняются через `SPRING_DATASOURCE_URL`,
`SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`.
Адрес статистики в основном сервисе задаётся через `STATS_SERVER_URL`.

## Структура

| Модуль | Назначение |
| --- | --- |
| `ewm-service` | События, пользователи, категории, заявки и подборки |
| `stats-server` | Сохранение обращений и агрегирование статистики |
| `stats-client` | HTTP-клиент сервиса статистики |
| `stats-dto` | DTO, общие для клиента и сервера статистики |

Это два запускаемых приложения и две библиотеки. У приложений разные базы;
основной сервис обращается к статистике только через HTTP.

В основном сервисе пакеты разделены по предметным областям. Контроллер принимает
и проверяет запрос, сервис выполняет бизнес-операцию, репозиторий работает с БД.
Транзакции находятся в сервисном слое. `EventStorageService` и
`CompilationStorageService` выполняют операции с БД и возвращают готовые DTO.
Фасады `EventService` и `CompilationService` получают статистику за пределами
транзакций. Для API используются отдельные DTO;
JPA-сущности наружу не возвращаются. Обработка ошибок централизована.

Публичные, пользовательские и административные маршруты разделены. По ТЗ
аутентификацию выполняет внешний шлюз. Приложение проверяет принадлежность событий
и заявок пользователю из пути. Самостоятельная система входа не реализована.

## Основные правила

- Новое событие получает статус `PENDING`, а дата начала должна быть минимум
  через два часа. Пользователь может редактировать `PENDING` и `CANCELED`.
- Администратор публикует только `PENDING`. Между публикацией и началом события
  должен оставаться минимум час. Опубликованное событие отклонить нельзя.
- Публичная выдача содержит только опубликованные события. Если обе границы
  времени отсутствуют, возвращаются будущие события.
- Одна пара пользователь/событие соответствует одной заявке. Ограничение
  уникальности есть и в БД, поэтому повторные запросы не создают дубликаты.
- Создание, подтверждение и отмена заявки блокируют строку события внутри
  транзакции. Это согласует проверку свободных мест и изменение заявки.
- При заполнении лимита остальные ожидающие заявки отклоняются одним SQL UPDATE. Весь пакет
  идентификаторов проверяется до изменения статусов.
- В PATCH пропущенные и `null` поля сохраняют старые значения; `false`, `0` и
  пустой список событий подборки применяются как новые значения.
- `from` — число пропущенных записей, а не номер страницы.
- Удаление категории с событиями запрещено. Удаление пользователя очищает его
  события и связанные заявки; удаление подборки сохраняет сами события.

## Статистика и выборки

`GET /events` и успешный `GET /events/{id}` записывают URI и IP клиента.
Просмотры конкретного события считаются по уникальным IP с момента публикации
для приложения из `spring.application.name` и URI `/events/{id}`. При подробном просмотре текущий
запрос записывается перед чтением счётчика.

Статистика поддерживает обычный подсчёт и подсчёт уникальных IP внутри каждой
пары app/URI. Границы времени включаются в диапазон. Даты запросов имеют формат
`yyyy-MM-dd HH:mm:ss`; оба контейнера используют `UTC`.

Связанные категории и инициаторы загружаются вместе с событиями. Подтверждённые
заявки считаются одним агрегирующим запросом. Просмотры запрашиваются пакетами
до 100 URI, чтобы длина URL оставалась ограниченной.

При `EVENT_DATE` пагинация выполняется в БД без запроса общего числа строк.
Подборки сначала выбираются по ID страницы, затем одним запросом загружаются
их события; пагинации поверх коллекционного JOIN нет. Списки пользователей
и категорий также не выполняют ненужный `COUNT(*)`.

При `VIEWS` идентификаторы подходящих событий читаются партиями по 100 с условием
`id > последний ID`. Верхний ID фиксируется до обхода, поэтому новые записи
не продлевают его бесконечно. Для каждого пакета получаем просмотры, сохраняя
только лучшие `from + size` пар ID/счётчик. Затем загружаем полные события и
считаем заявки только для итоговой страницы. Равные просмотры упорядочены по ID.
Это сохраняет общий порядок без загрузки всех JPA-сущностей в память.

Существующий API статистики требует прочитать просмотры всех подходящих ID,
поэтому время точной сортировки по-прежнему растёт с числом кандидатов, а память
для ранжирования — со значением `from + size`. Все пакеты используют одну верхнюю
границу времени; общего транзакционного снимка двух баз нет. Для существенно
больших объёмов понадобится отдельная модель чтения со счётчиками просмотров.

Вызовы статистики ограничены таймаутами подключения 2 секунды и чтения 3 секунды.
При её недоступности операции, которым требуется статистика, возвращают 503.
Нулевые просмотры вместо ошибки не подставляются. При чтении сначала формируются
DTO в короткой транзакции, затем запрашивается статистика. При изменении события
или подборки статистика запрашивается до write-транзакции: её недоступность
не оставляет сохранённого изменения. Поле `views` в таком ответе отражает снимок
перед записью. Внутри write-транзакции состояние и права проверяются повторно под
блокировкой строки. PATCH подборки без замены событий также проверяет, что её
состав не изменился во время HTTP; иначе возвращает 409 и не применяет PATCH.

Docker Compose проверяет `/actuator/health` обоих приложений. Основной сервис
стартует после готовности своей БД и сервиса статистики.

## Проверки

```shell
mvn test
mvn clean install -P check
```

Профиль `check` запускает исходные правила Checkstyle и SpotBugs из шаблона курса.
JUnit-тесты используют H2 в режиме PostgreSQL; в runtime зависимость H2 не входит.
Проверяются валидация API, фильтры, произвольный offset, жизненный цикл событий,
обработка заявок, откат транзакции и конкурентная запись на последнее место.
Дополнительные проверки контролируют число SQL-запросов, загрузку только нужных
сущностей, массовое отклонение и отсутствие транзакции при обращении к статистике.
Для Mockito используется обычное создание подклассов, без подключения Java agent.

## Комментарии к событиям

Дополнительная функциональность реализована в ветке `feature_comments` от `main`.

| Метод | Путь | Назначение | Успешный ответ |
| --- | --- | --- | --- |
| POST | `/users/{userId}/events/{eventId}/comments` | Добавить комментарий | 201 |
| PATCH | `/users/{userId}/comments/{commentId}` | Изменить свой комментарий | 200 |
| DELETE | `/users/{userId}/comments/{commentId}` | Удалить свой комментарий | 204 |
| DELETE | `/admin/comments/{commentId}` | Удалить комментарий администратором | 204 |
| GET | `/events/{eventId}/comments?from=0&size=10` | Список комментариев события | 200 |

POST и PATCH принимают `{"text":"Текст комментария"}`. Текст обязателен, не может
состоять только из пробельных символов и ограничен 2000 символами. PATCH заменяет
текст целиком. Идентификатор, автор, событие и время создания определяются сервером;
передача этих полей в теле запроса не изменяет их.

Ответ содержит `id`, `text`, `event` (ID события), `author` (`id` и `name`),
`created` и `updated`. Даты имеют формат `yyyy-MM-dd HH:mm:ss` в UTC; `updated`
равно `null` до первого редактирования. Email автора публично не возвращается.

Комментировать можно только опубликованные события. Комментарий не требует заявки
на участие; организатор тоже может отвечать в комментариях своего события.
Редактирование и пользовательское удаление доступны только автору.
Администратор может удалить любой комментарий. Удаление физическое; повторное
удаление возвращает 404. Удаление автора или события удаляет связанные комментарии,
а удаление комментария не затрагивает автора и событие.

Публичный список доступен только для опубликованного события и сортируется по
`created DESC, id DESC`. `from` — точное смещение, `size` — положительный размер
страницы. Значения по умолчанию: 0 и 10. Пустой список и смещение за его пределами
возвращают `[]`. Пагинация выполняется в БД; авторы загружаются вместе с комментариями,
без отдельных запросов на каждую запись и без подсчёта общего количества.
Эндпоинты комментариев не обращаются к статистике и не увеличивают просмотры события.

Ошибки возвращаются в общем формате `ApiError`:

- 400 — неверное тело, идентификатор или параметры пагинации;
- 404 — объект не найден, чужой комментарий при изменении/удалении либо
  непубличное событие при чтении;
- 409 — попытка добавить комментарий к неопубликованному событию.

## Postman

Коллекция находится в `postman/feature.json`. Импортируйте её в Postman и запустите
целиком либо выполните после запуска обоих сервисов:

```shell
newman run postman/feature.json
```

Адрес основного сервиса задаётся переменной `baseUrl`, по умолчанию
`http://localhost:8080`. Коллекция создаёт пользователей, категорию и события с
уникальными значениями, проверяет успешные ответы, права, валидацию, пагинацию
и каскадное удаление, затем удаляет свои данные. Её можно запускать повторно
после стандартных коллекций основного сервиса и статистики.
